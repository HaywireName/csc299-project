## Project Planning and Initiation

The development process of the project started with an outline of a terminal-based Personal Knowledge Management System with task management, document storage and interaction, chatbot, and agentic capabilities using AI models. I created two distinct outlines, one for a GUI-based web application (Outline.md) and another for a CLI-based terminal program (CLI [Outline.md](http://Outline.md)), made to correct the first one. This dual-outline problem revealed a lesson: the importance of aligning vision with technical requirements early. The web-based outline included drag-and-drop cards, visual PDF viewers, and mouse interactions, while the assignment specifically required a terminal interface. This mismatch required me to reinvision the program while trying to keep as many features as possible through a CLI-based project.

Once the CLI outline was done, a comprehensive specification process began by using a chatbot to craft prompts for me to enter into Copilot. Rather than diving directly into coding, structured planning documents were created: a detailed outline breaking the project into four modules (PKMS/PDF management, task management, chatbot, and AI agents), along with technical considerations like JSON storage, OpenAI API integration, and cross-platform compatibility, and then user functionality choices for more commands and ease of use. This upfront planning proved invaluable, as it provided a clear roadmap that prevented scope creep and feature confusion during implementation, and gave me a clear length of what the program would need and how it would work.

## AI-Assisted Prompts

The development process used a multi-layered AI assistance approach by combining Claude AI, for architectural planning, and GitHub Copilot for code generation. Claude served as an architect, generating comprehensive Speckit-style prompts that broke down each feature into discrete, implementable steps and giving testing and confirmation routes to check if the code worked. These prompts were meticulously detailed, specifying exact function signatures, error handling requirements, data structures, and file organization. Each prompt followed a consistent format: context establishment, specific requirements enumerated, expected code structure, example interactions, and critical reminders about production-ready practices.

GitHub Copilot functioned as the coder, receiving these prompts and generating actual Python code. The workflow followed a strict pattern: receive Speckit-style prompt from Claude, paste into Copilot, review generated code, test immediately, debug if necessary, commit and proceed to next prompt only after verification. This incremental approach — completing Prompts labeled in order before encountering issues — demonstrated the value of modular development with immediate feedback loops, especially when it comes to fixing bugs that only appear due to one addition. They allowed me to fine tune how the each addition looks and performs and made it easier for me to focus on functionality for use-case scenarios by not having to worry about the layout and implementation of the code. 

## Technical Challenges and Solutions

Several significant obstacles emerged during development, each requiring different problem-solving approaches. The first major challenge involved API key security. Initial prompts opted to use *.env* file management, but I had concerns about committing secrets to source control, leading to a review of how keys could be managed only on user-side. Claude provided three alternative approaches: system environment variables, encrypted local storage, and OS keyring integration, which is how I began to learn not only what methods are possible, but how artificial intelligence can produce overpowered solutions, like the keyring one, to boost the program into higher levels of functionality. After analysis, the system environment variable approach was adopted, requiring updates to multiple development prompts to remove .env dependencies and add *get\_api\_key()* functions that checked the system directly.

The second critical issue was codebase clutter and a need to refactor the codebase. While developing the program, I made the mistake of asking it to create documentation with stored in 2 separate documents, user documentation and developer documentation. I did this without noticing one of the last prompts that Claude had for the program was to implement concise documentation, as well as the AI starting to create a new document for every addition and change to the program, instead of keeping it to 2 documents. By Prompt 4.1, the project contained approximately 30+ files including numerous test scripts, demo files, example code, and scattered documentation across multiple markdown files. This clutter emerged because Copilot, by default, generates verification scripts and examples for each feature. The solution involved creating a comprehensive cleanup prompt that: (1) audited all files categorizing them as Essential, Remove, or Combine, (2) consolidated documentation into three documentation markdown files, README.md, USER\_GUIDE.md, DEVELOPER\_GUIDE.md, (3) generated a safe cleanup script that archived rather than deleted files for reference when creating new documentation, and (4) established "production-ready code requirements" to append to all future prompts, explicitly forbidding test file creation. The process for this refactor was long, and ended up with me scrapping that version of the project as a prototype, to start the prompts over and waiting to create documentation until the end, only because that’s how it was already laid out in the prompts. I personally would update documentation with each addition to the program, but did not want to mess around with the AI’s logic for too long, trying to focus on having enough context for my vision on implementations. So, I used Copilot’s suggestion to hold on documentation. This led to a nice addition to the creation prompts that told Copilot not to create documentation, tests, or scripts, and to find other, less automated ways inside the program to debug. This process worked, and taught me how important it is to have a clear set of knowledge about the project, and have specifications in prompts. 

A particularly complex problem arose from version control confusion — different project versions had divergent command implementations, resulting in "ghost commands" (documented but not implemented), "missing registrations" (implemented but not registered), and "broken commands" (registered but crashing). This required developing a sophisticated validation prompt that cross-referenced four sources: the command registry, module implementations (scanning for *cmd\_\** functions), help text output, and USER\_GUIDE.md documentation. The validation prompt generated an inventory table showing each command's registration status, implementation status, documentation status, and working status, then provided specific fixes with file paths and line numbers. In the end, however, the codebase was too cluttered in an unoperational state and the model started to get worse at following along with the codebase for troubleshooting and additions. This led to me scrapping that version of the prototype, and using what I learned for the next one. 

## Lessons and Implications

This development process taught me important principles for AI-assisted software development. AI coding assistants excel with precise, contextual prompts but can struggle with implicit requirements when there’s a lack of context. The developer's role switches from general coding to architectural design, prompt engineering, and quality assurance. Iterative development with immediate validation catches AI-generated errors early when they're cheapest to fix. Finally, explicit prevention (through prompt rules) works better than reactive cleanup—establishing constraints upfront prevents problems rather than fixing them later.

The project's 50% completion provided a good checkpoint for reflection and course correction, demonstrating that mid-project cleanup and process refinement are crucial for maintaining code quality in AI-assisted development, and to try and idealize prevention. The biggest strength in Claude’s program prompts were the examples it gave for input and output. This allowed Copilot to be much more successful in its inferences on getting the code to work with the specified output. 

## Success Factors

Several strategies proved essential for project success. First, the Speckit approach—detailed, structured prompts with explicit requirements—drastically reduced ambiguity and prevented Copilot from making sudden architectural decisions. Second, creation with an addition to the prompt to hold on documentation and miscellaneous scripts for testing prevented unnecessary clutter and time consumption, even if it could be easily solved. Third, maintaining three consolidated documentation files (instead of scattered markdown) kept the project navigable and maintainable. Fourth, using both Copilot and Claude for suggestions on the program and prompts helped me extend my vision to be able to use the program more for knowledge interaction and think of interactions I had not thought of before, like making connections between stored documents and task to create a small report on what else you might need to work on.
